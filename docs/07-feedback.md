# 7. Обратная связь

Цель беты — понять, где ассистент помогает, а где нет. Помогают два
канала: выгрузка телеметрии и Issues.

Сервер **ничего не отправляет сам**. Данные лежат у вас, пока вы не пришлёте
архив.

## Выгрузка телеметрии

1. Откройте дашборд: `http://<хост>:3100/dashboard/` → **Выгрузка телеметрии**.
2. Выберите период. Максимум — 92 дня за один архив.
3. Переключатель **«Включить ответы инструментов»**: включённый добавляет в архив
   текст, который сервер вернул модели. Это самое полезное для разбора —
   видно, что именно модель прочитала. Строки данных из базы туда всё равно не
   попадают.
4. Страница покажет, сколько записей и примерный размер архива **до**
   скачивания.
5. Скачайте zip и приложите его к Issue.

Удобная периодичность — раз в 1–2 недели.

> ВАЖНО!!! Если опасаетесь передачи через Issues, то можете отправить письмо c телеметрией [тех поддержке](mailto:support@wshcmai.ru).
>

## Что внутри архива

| Файл | Что в нём |
| --- | --- |
| `README.txt` | что в архиве и что замаскировано |
| `manifest.json` | период, версии, число записей, контрольные суммы, счётчики маскирования |
| `env.jsonl` | окружение каждого запуска: версии MCP и HCM, СУБД, режимы, состояние лицензии |
| `sessions.jsonl` | подключения клиентов: приложение, версия, модель |
| `calls.jsonl` | вызовы инструментов: вход, время, признаки повторов и ошибок, ответ (если включили) |
| `feedback.jsonl` | отзывы модели |

Это обычный zip с текстовыми файлами — откройте и посмотрите перед отправкой.

## Персональные данные

Маскирование выполняется **при записи**, а не при выгрузке, и отключить его
нельзя:

- строки данных из базы не сохраняются никогда — 
  только текст запроса, имена колонок и число строк;
- строковые литералы в SQL заменяются на `'<str>'`, числа из 5–12 цифр — на
  `<num>`;
- в тексте запросов, ответов, ошибок и отзывов e-mail, телефоны, паспорт,
  СНИЛС, ИНН, номера карт, даты и ФИО заменяются на `<email>`, `<phone>`,
  `<passport>`, `<snils>`, `<num>`, `<card>`, `<date>`, `<fio>`, `<name>`;
- IP-адреса, логины, токены, пути к файлам и имена пользователей ОС не
  записываются;
- идентификатор установки — случайный, с людьми не связан.

Маскер работает по правилам и не гарантирует, что распознает любую фамилию в
свободном тексте. Если вы увидели в архиве что-то лишнее — напишите об этом в
Issue (сам фрагмент присылать не нужно, достаточно файла и номера строки):
правило поправим.

## Логи

Логи лежат в каталоге `logs/` рядом с `docker-compose.yml`:

| Файл | Что в нём | Срок |
| --- | --- | --- |
| `app-*.log` | общий лог сервера | ротация по дням |
| `startup-*.log` | этапы загрузки | ротация по дням |
| `errors-*.log` | только ошибки | ротация по дням |
| `access-*.log` | HTTP-запросы | ротация по дням |
| `mcp-usage-*.log` | вызовы инструментов (то же, что в выгрузке) | 100 дней |

`docker compose logs` — отдельный поток: то же самое, но в выводе Docker.

Если сервер не поднимается или ведёт себя странно, приложите к Issue
`startup-*.log` и `errors-*.log` за нужный день. В выгрузку телеметрии они не
входят.

## Issues

Шаблоны уже настроены:

- **Обратная связь** — сюда архив телеметрии и впечатления;
- **Ошибка** — что делали, что ожидали, что получилось, версия и логи;
- **Не хватает возможности** — пожелания по доработкам;
- **Неверный ответ** — если ответ не совпадает с ожиданиями;
- **Вопрос** — всё остальное.

В любом случае укажите `version` и `built_at` из ответа
`curl http://<хост>:3100/healthz`.

**Не вставляйте в Issue пароли базы и `MCP_AUTH_TOKEN`.** Issues публичны.

## Что особенно интересно

- Инструмент ответил не то, что вы ожидали, — с каким запросом.
- Модель не нашла нужного и пошла писать SQL руками.
- Чего вообще не хватает: какой объект или сценарий платформы стоило бы
  добавить.
- Сколько времени сервер экономит (или не экономит) на реальной задаче.
