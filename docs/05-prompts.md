# 5. Правила для модели

В каталоге [prompts/](../prompts/) лежит пример готового правила: когда модель
**обязана** обратиться к MCP-серверу вместо того, чтобы писать код по памяти.
Без них модель пользуется инструментами эпизодически — выдумывает имена полей
и функций, как и раньше.

## О чём эти правила

- **Обязательно спросить сервер** перед тем, как писать: SQL по таблице
  платформы, обращение к полю объекта, вызов функции SP-XML, JOIN двух
  объектов, обработчик системного события, код операции документооборота,
  удалённое действие, выборку, агента, показатель, Web-шаблон, отчёт,
  уведомление, вызов функции библиотеки.
- **Полезно спросить** — типовые пути, по которым находки сами наводят на
  нужный инструмент.
- **Не стоит звать** — `list_objects` без явной просьбы и `get_lists` без
  запроса: они длинные и засоряют контекст.
- Одного подтверждения в рамках диалога достаточно: повторно дёргать
  инструмент за тем же ответом не нужно.

В конце задачи правила просят модель вызвать `record_feedback` — это и есть
самый полезный feedback от LLM модели: какие инструменты помогли, чего не хватило и
какая модель работала. Данные остаются у вас в `logs/`, пока вы сами не
пришлёте выгрузку.

## Свой текст

Правила — отправная точка, а не идеал. Если в вашей команде свои соглашения
по коду, допишите их рядом; если какой-то инструмент модель зовёт слишком
часто или зря — уберите строку. Что получилось изменить и почему, можете написать в
[Issues](../../../issues): это поможет сделать правила лучше для всех.
